# 实验一：自定义 ROC 分析类实现思路与代码详解

## 1. 这次实验要解决什么问题

本实验要求在北太天元环境中设计一个名为 `MyROC` 的类，用于完成二分类模型的 ROC 分析。给定真实类别标签 `labels` 和分类器输出的正类得分 `scores`，程序需要计算不同阈值下的假阳性率 `FPR`、真阳性率 `TPR`，再用梯形积分法计算 ROC 曲线下面积 `AUC`，最后绘制符合要求的 ROC 图。

本实验最终形成两个核心代码文件：

- `MyROC.m`：类定义文件，实现输入检查、ROC 计算、AUC 计算和绘图。
- `testMyROC.m`：主测试脚本，加载 `data1.mat`、`data2.mat`、`data3.mat`，调用 `MyROC` 类，并保存运行结果图。
- `pairwiseAUC.m`：AUC 独立验证函数，用于和 `MyROC` 的结果做交叉检查。

此外，测试脚本中额外加入了一个重复得分测试 `tie_test`，用于验证当多个样本具有相同预测得分时，程序是否仍能正确计算 ROC 和 AUC。

## 2. ROC 曲线的基本含义

ROC 曲线用于评价二分类模型在不同分类阈值下的表现。分类器通常不会直接输出 0 或 1，而是输出一个正类得分。例如某个样本的得分越高，就越可能属于正类。

对于某一个阈值 `threshold`，可以规定：

```text
Scores >= threshold
```

的样本被判为正类，其余样本被判为负类。随着阈值从高到低变化，被判为正类的样本会越来越多。每一个阈值都会产生一组混淆矩阵统计量：

- `TP`：真正例，实际为 1 且预测为 1。
- `FP`：假正例，实际为 0 但预测为 1。
- `TN`：真负例，实际为 0 且预测为 0。
- `FN`：假负例，实际为 1 但预测为 0。

ROC 曲线关注两个指标：

```text
TPR = TP / P
FPR = FP / N
```

其中 `P` 表示正类样本总数，`N` 表示负类样本总数。`TPR` 越高说明正类识别得越充分，`FPR` 越低说明负类误判越少。ROC 曲线越靠近左上角，分类器效果越好。

## 3. AUC 的基本含义

AUC 是 ROC 曲线下面积。它可以理解为：随机抽取一个正类样本和一个负类样本，分类器给正类样本更高得分的概率。AUC 的常见解释如下：

- `AUC = 1`：分类器能完全区分正负样本。
- `AUC > 0.5`：分类器优于随机猜测。
- `AUC = 0.5`：分类器接近随机猜测。
- `AUC < 0.5`：分类方向可能反了，或者数据、计算过程有问题。

本实验按题目要求使用梯形法计算 AUC：

```text
obj.AUC = trapz(sortedFPR, sortedTPR);
```

## 5. MyROC 类整体设计

`MyROC` 类中定义了五个属性：

```text
properties (SetAccess = private)
    Labels
    Scores
    FPR
    TPR
    AUC
end
```

这些属性的含义如下：

| 属性 | 含义 |
|---|---|
| `Labels` | 真实类别标签，要求只包含 0 和 1 |
| `Scores` | 分类器输出的正类预测得分 |
| `FPR` | 不同阈值下的假阳性率 |
| `TPR` | 不同阈值下的真阳性率 |
| `AUC` | ROC 曲线下面积 |

这里使用了：

```text
properties (SetAccess = private)
```

这样外部程序可以读取对象属性，但不能随意修改属性。这个设计是为了避免外部修改了 `Labels` 或 `Scores`，却没有重新计算 `FPR`、`TPR` 和 `AUC`，从而导致对象内部数据不一致。

类中主要包含四个方法：

| 方法 | 作用 |
|---|---|
| `MyROC(labels, scores)` | 构造函数，完成输入检查、保存数据、自动计算 ROC 和 AUC |
| `computeROC(obj)` | 根据标签和得分计算 ROC 曲线点 |
| `computeAUC(obj)` | 调用 `trapz` 计算 AUC |
| `plotROC(obj)` | 绘制 ROC 曲线、随机分类器参考线和 AUC 标注 |

## 6. 构造函数的设计

构造函数负责初始化对象。实验要求中明确规定：

- `labels` 和 `scores` 长度必须一致。
- `labels` 只能取 0 或 1。
- 构造函数应自动调用 `computeROC()` 和 `computeAUC()`。

代码中的主要检查如下：

```text
if nargin ~= 2
    error('构造函数必须同时输入labels和scores。');
end
if ~(isnumeric(labels) && isnumeric(scores))
    error('labels和scores必须为数值向量。');
end
if ~(isvector(labels) && isvector(scores))
    error('labels和scores必须为向量。');
end
if isempty(labels) || isempty(scores)
    error('labels和scores不能为空。');
end
if numel(labels) ~= numel(scores)
    error('labels和scores长度必须一致。');
end
```

这些检查可以防止输入数据格式错误。例如，如果 `labels` 和 `scores` 长度不同，ROC 计算就没有意义；如果输入不是向量，也不符合题目要求。

之后代码把输入统一转换为列向量：

```text
labels = labels(:);
scores = scores(:);
```

这样做的好处是，无论用户输入的是行向量还是列向量，类内部都用统一格式处理，避免后续维度不一致。

接着检查标签和得分：

```text
if ~all(labels == 0 | labels == 1)
    error('labels只能包含0和1。');
end
if ~all(isfinite(scores))
    error('scores不能包含NaN或Inf。');
end
if ~(any(labels == 1) && any(labels == 0))
    error('labels必须同时包含正类1和负类0，否则ROC曲线和AUC无定义。');
end
```

这里特别处理了单类标签问题。如果 `labels` 中只有正类或只有负类，`TPR` 或 `FPR` 的分母会为 0，ROC 和 AUC 在数学上无定义。因此当前版本选择直接报错，而不是勉强返回一个容易误导的数值。

最后保存数据并自动计算：

```text
obj.Labels = labels;
obj.Scores = scores;
obj = obj.computeROC();
obj = obj.computeAUC();
```

这样用户只需要写：

```text
rocObj = MyROC(labels, scores);
```

对象就已经包含了完整的 `FPR`、`TPR` 和 `AUC`。

## 7. computeROC 的核心算法

### 7.1 为什么不逐阈值扫描全部样本

最直接的做法是先生成一组阈值，然后对每个阈值都扫描全部样本，判断哪些样本被预测为正类。这个方法容易理解，但效率较低。如果样本数为 `n`，阈值数接近 `n`，那么时间复杂度接近：

```text
O(n^2)
```

对于本实验的 `data3.mat`，样本数为 2000，还可以接受；但如果样本数变成几万或几十万，逐阈值扫描就会明显变慢。

因此当前版本采用更标准的做法：

```text
按 scores 降序排序 -> 按相同分数组处理 -> 增量累计 TP 和 FP
```

这个方法主要耗时在排序上，时间复杂度约为：

```text
O(n log n)
```

### 7.2 排序和同分组

代码首先按预测得分降序排序：

```text
[sortedScores, sortIndex] = sort(scores, 'descend');
sortedLabels = labels(sortIndex);
```

排序后，高分样本排在前面。阈值从高到低移动时，相当于把排序后的样本一批一批纳入“预测正类”集合。

接着找出每一个唯一得分组的结束位置：

```text
scoreChangeIndex = [find(diff(sortedScores) ~= 0); numel(sortedScores)];
```

解释一下这句：

- `diff(sortedScores)` 计算相邻得分的差。
- 如果差不为 0，说明从当前位置到下一个位置发生了得分变化。
- `find(diff(sortedScores) ~= 0)` 找到所有得分变化的位置。
- `numel(sortedScores)` 加上最后一个样本位置，保证最后一组也会被处理。

这样做可以保证相同得分样本被放在同一组里统一处理。这样 ROC 结果不会受到相同得分样本内部顺序的影响。

### 7.3 初始化 ROC 点

代码为 `FPR` 和 `TPR` 预分配空间：

```text
fpr = zeros(numel(scoreChangeIndex) + 2, 1);
tpr = zeros(numel(scoreChangeIndex) + 2, 1);
```

这里多出来的 2 个点分别对应：

- 第一个点：阈值为 `+Inf`，所有样本都判为负类，ROC 点为 `(0,0)`。
- 最后一个点：阈值为 `-Inf`，所有样本都判为正类，ROC 点为 `(1,1)`。

题目要求必须包含 `+Inf` 和 `-Inf` 两种极端情况，所以这里显式保留这两个端点。由于处理完最后一个唯一得分组后，ROC 已经到达 `(1,1)`，最后的 `-Inf` 端点会和前一个点重合。这个重复点不影响 `trapz` 计算，因为它的横坐标变化为 0，贡献面积为 0；但它能清楚体现极端阈值已经被覆盖。

### 7.4 增量累计 TP 和 FP

核心循环如下：

```text
truePositive = 0;
falsePositive = 0;
previousIndex = 1;

for i = 1:numel(scoreChangeIndex)
    currentIndex = scoreChangeIndex(i);
    groupLabels = sortedLabels(previousIndex:currentIndex);

    truePositive = truePositive + sum(groupLabels == 1);
    falsePositive = falsePositive + sum(groupLabels == 0);

    tpr(i + 1) = truePositive / positiveCount;
    fpr(i + 1) = falsePositive / negativeCount;
    previousIndex = currentIndex + 1;
end
```

这段代码的逻辑是：

1. 初始时阈值非常高，没有任何样本被判为正类，所以 `TP = 0`，`FP = 0`。
2. 每处理完一组同分样本，就把这一组中的正类样本数加到 `TP`，把负类样本数加到 `FP`。
3. 用当前累计的 `TP` 和 `FP` 计算新的 `TPR` 和 `FPR`。
4. 重复这个过程，直到所有样本都被纳入预测正类集合。

最后显式设置 `-Inf` 端点：

```text
fpr(end) = 1;
tpr(end) = 1;
```

## 8. computeAUC 的设计

`computeAUC()` 的作用是用梯形法计算 ROC 曲线下面积。

代码先检查 `FPR` 和 `TPR` 是否已经存在。这里没有使用三参数 `assert`，而是使用 `if + error`，因为北太天元的 `assert` 不支持带错误 ID 的写法：

```text
if isempty(obj.FPR) || isempty(obj.TPR)
    error('请先调用computeROC计算FPR和TPR。');
end
if numel(obj.FPR) ~= numel(obj.TPR)
    error('FPR和TPR长度必须一致。');
end
```

然后检查 `FPR` 是否非递减：

```text
if ~all(diff(sortedFPR) >= -eps)
    error('FPR必须按升序排列，请先重新调用computeROC。');
end
```

这里没有采用无条件排序 `FPR/TPR` 的方式。原因是 ROC 曲线可能存在相同 `FPR` 的垂直段，如果随意排序，可能改变同一横坐标下点的上下顺序。当前做法是在 `computeROC()` 中保证输出顺序正确，然后在 `computeAUC()` 中做防御性检查。

最终调用：

```text
obj.AUC = trapz(sortedFPR, sortedTPR);
```

这正好符合题目要求中“直接调用北太天元内置函数 `trapz(FPR, TPR)` 进行数值积分”的要求。

## 11. AUC 交叉验证

为了证明 `MyROC` 计算结果可靠，测试脚本中加入了独立的 `pairwiseAUC()` 验证方式。

### 11.1 pairwiseAUC 验证

`pairwiseAUC()` 使用 Wilcoxon-Mann-Whitney 统计量验证 AUC。该函数已单独保存为 `pairwiseAUC.m`，这样比把函数写在脚本末尾更兼容北太天元。其思想是比较每一个正类样本和每一个负类样本：

- 如果正类得分大于负类得分，记 1 分。
- 如果正类得分等于负类得分，记 0.5 分。
- 如果正类得分小于负类得分，记 0 分。

最终得分除以所有正负样本对数量，就得到 AUC。

代码如下：

```text
function auc = pairwiseAUC(labels, scores)
    labels = labels(:);
    scores = scores(:);
    positiveScores = scores(labels == 1);
    negativeScores = scores(labels == 0);
    pairCount = numel(positiveScores) * numel(negativeScores);
    winCount = 0;

    for i = 1:numel(positiveScores)
        winCount = winCount + sum(positiveScores(i) > negativeScores);
        winCount = winCount + 0.5 * sum(positiveScores(i) == negativeScores);
    end

    auc = winCount / pairCount;
end
```

这个方法和梯形积分法是不同角度的 AUC 定义。二者结果一致，说明 `MyROC` 的计算过程可信。

## 14. 为什么 ROC 点数比唯一得分数多

当前版本显式保留了 `+Inf` 和 `-Inf` 两个极端阈值端点。因此 ROC 点数为：

```text
唯一得分数量 + 2
```

例如 `data3.mat` 的唯一得分数量为 1748，因此 ROC 点数为 1750。

其中 `+Inf` 对应 `(0,0)`，表示没有样本被预测为正类；`-Inf` 对应 `(1,1)`，表示所有样本都被预测为正类。最后一个点可能和处理完最低得分组后的点重合，但这不影响 AUC，因为重复点横坐标差值为 0，不产生额外面积。

保留重复终点的原因是题目明确要求：

```text
必须包含阈值取 +∞ 和 -∞ 的极端情况，保证曲线从 (0,0) 到 (1,1) 完整
```

## 15. 当前实现相对基础版本的改进

当前版本在基础实现上做了几项改进：

1. 使用排序和同分组增量累计，提高计算效率。
2. 对重复得分样本统一处理，避免相同分数内部顺序影响结果。
3. 对单类标签直接报错，避免返回无定义的 AUC。
4. 使用 `SetAccess = private` 避免对象内部属性被外部随意修改。
5. 使用 `pairwiseAUC` 独立验证计算结果。
6. 绘图时根据 ROC 点数决定是否显示圆圈标记，兼顾美观和可读性。
7. 主程序自动保存运行日志和 ROC 图片，方便后续整理 PPT。
